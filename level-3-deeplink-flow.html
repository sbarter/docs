Level 3 Flow

Deep Link Linking

The player starts linking from inside the game. The Game Studio asks Sbarter for a one-time link for the player's game account, hands it to the player, and the player opens it in the Sbarter app. Sbarter does not call the Game Studio back; the studio checks the result with the link status endpoint.

Scope: The studio vouches for providerUserId (the player is logged in to the game); the player proves the Sbarter side by opening the link while signed in to Sbarter.
Step 1: VGP mints the link

POST /v1/linking/deeplink/generate

Step 2: VGP checks the result

POST /v1/linking/status

Before the first call

  • Client credentials. Create them in the Sbarter web portal (your studio → API credentials). The client needs the scopes linking.deeplink.write and linking.read; the token's scope claim shows what you hold.
  • providerGameId. Sbarter registers each of your games against your studio with a providerGameId, the id you use for the game in every call. It is set by Sbarter (it is not the game name shown in the portal) - ask Sbarter for it. An id that is not registered, or registered only as your studio's default entry, is refused.
  • Hosts. See Servers in the API reference: API partners.<env>.sbarter.com/<slug> (your slug is given by Sbarter), tokens from the Sbarter identity provider of the same environment. Credentials of one environment are refused by the others.

What happens when the player opens the link

  • The deepLink is an https link (https://connect.sbarter.com/linking/confirm/dl_... in production, connect.test.sbarter.com on staging). Hand it over whole; never rebuild it from linkId.
  • App installed: the link opens the Sbarter app directly.
  • App not installed: the link opens a Sbarter page showing your game and studio with the store links. After install, the app picks the pending link up on first start (Android via the install referrer; iOS asks once for permission to read it). The 15-minute lifetime still applies.
  • The app keeps the link until the player is signed in - including registration and PIN setup - and then redeems it. There is no separate confirmation step; the player sees Game connected with your providerDisplayName, game name and icon. Send providerDisplayName: it is how the player recognises their account.
  • With a destination, the app then opens that challenge or tournament.
  • Nothing is sent to the studio. Call POST /v1/linking/status when the game regains focus.

When the link does not link

Redemption is all-or-nothing: if it is refused, the link stays unused and nothing is linked. The studio sees it only as linked: false on the status call.

At generation time the same account check runs: a providerUserId that is already linked is refused with 467 GI0023 and no link is minted. The one exception is a challenge destination, which needs the account to be linked already (see Destination).

Destination

  • destination is optional: { "type": "challenge" | "tournament", "resourceId": "<Sbarter uuid>" }.
  • A challenge must be of the same game, waiting for an opponent, and not expired. A tournament must be of the same game and still open for registration.
  • The resourceId is a Sbarter id, not one of yours. Take a challenge id from GET /v1/challenges; there is no client-credentials endpoint to list tournaments yet, so take a tournament id from your Sbarter web portal or ask Sbarter.
  • A challenge destination is for a player who is already linked, and a private challenge only for a player invited to it; otherwise 403. A tournament destination also works for a player who is not linked yet.
  • Anything that fails the other checks is a 404 and no link is minted.
