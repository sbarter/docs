Level 3 Flow

Web Game Launch

A web game is played inside the Sbarter app. The player never signs up in the game and never links an account: Sbarter creates the game account server to server. When both players are ready, each taps Start match, the app opens the game page in its WebView with a one-time launch code, and the game's backend redeems the code to learn which match, player and seat it is.

Scope: Only a redeemed launch code lets a player in. A copied game URL, a code without its verifier, a reused code, the other player's seat and another studio's code all fail.
Sbarter calls you

POST /v1/sbarter/gamer/provision, POST /v1/session (return matchId)

The app opens your page

Form POST to your launch URL: launchCode, codeVerifier

You call Sbarter

POST /v1/game-launches/redeem, then the match result

Before the first match

  • Launch URL. The HTTPS page the app opens for your game, per environment, given to Sbarter at onboarding. Only HTTPS origins you registered are allowed in the WebView. It is not your website link.
  • Client credentials with launch.redeem and webhook.write, created in the Sbarter web portal. The token's scope claim shows what you hold.
  • Base URL and API key for Sbarter → studio calls, entered in the Studio Web Portal, as for every Level 3 game.

Player accounts

  • playerId is an opaque UUID per player and per studio: stable for that player, different at every studio, never the Sbarter user id. No personal data comes with it.
  • Use it as the account key. From then on it is the player's providerUserId in every call, both ways.
  • The call is idempotent on playerId: 201 the first time, 200 and no change on a repeat. Sbarter repeats it after a timeout or a 5xx.

Match registration

  • Each player's internalId and providerUserId both carry the player's playerId.
  • Players are ordered by seat: 1 is the challenge creator, 2 the opponent.
  • Answer with {"matchId": "..."} - required for web games - and the same matchId when the same sessionId is registered again.
  • The match is offered to the players only after registration succeeded.

Launch and redeem

  • Your page receives launchCode and codeVerifier as application/x-www-form-urlencoded. Send both to POST /v1/game-launches/redeem from your backend.
  • Trust only the redeem answer (providerGameId, sessionId, matchId, playerId, seat, matchExpiresAt). Ids in a page URL identify nothing.
  • Start a session for that seat (e.g. a Secure, HttpOnly cookie scoped to your host), redirect to a clean URL, and enforce the seat on every gameplay request and WebSocket.
  • A code lives 60 seconds and works once. A player who opens the game again comes with a new code: replace their previous play session for that seat.
  • End access when the match is over or matchExpiresAt has passed. Keep the code and the verifier out of URLs, logs and analytics.

Errors from redeem

StatusMeaningWhat to do
467 GI0030Unknown, expired or used code, a code for a game that is not yours, or a verifier that does not match - one answer for all, so codes cannot be probedShow a way back to the app; the player taps Start match again
400Body does not match the schemaFix the request
401 / 403Token missing or expired / no launch.redeem, or no User-Agent (HTML body)Fix credentials
503Sbarter temporarily unavailableRetry with the same code while it is valid

Do not repeat a redeem that may have succeeded: the code is consumed. If the answer was lost, the player gets a new code by tapping Start match again.

Result

  • Send it to the webhookUrl of the registration, as for any Level 3 game.
  • matchId must be the one you returned at registration; another one is refused with 409.
  • Identify each player by their playerId in providerUserId and internalId.
  • Your result is final: web games have no dispute and no manual result reporting in Sbarter. Retries are safe on sessionId + matchId.
